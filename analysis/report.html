壽星日是我做的一個網站，收台灣的生日優惠。做網站的時候只在意「怎麼顯示」， 從來沒認真問過這批資料本身長什麼樣子。這一頁把它丟進 SQLite 問九個問題： 哪一類最大方、多少優惠其實當天辦來不及、住不同縣市差多少、 還有這批資料自己有多可信。

每一節都是「問題 → 一句結論 → 圖 → SQL → 表格」。 結論的數字是從查詢結果算出來的，不是寫死的字串； 資料換一版，這一頁的數字會自己跟著換。

-- Q1 這批生日優惠長什麼樣子？（報告開頭的幾個數字）
--
-- 一列就講完整體規模。寫法上刻意用 sum(case when ...) 而不是跑好幾個 count(*)，
-- 只掃一次 offers 就把所有比例算出來。
select
    count(*)                                               as n_offers,
    count(distinct brand)                                  as n_brands,
    count(distinct group_name)                             as n_groups,
    count(distinct category)                               as n_categories,
    sum(case when is_nationwide = 1 then 1 else 0 end)     as n_nationwide,
    sum(case when verified = 1 then 1 else 0 end)          as n_verified,
    sum(case when validity_type = 'rolling' then 1 else 0 end) as n_rolling,
    sum(case when membership_cost = 'free'
              and coalesce(advance_days, 999) = 0 then 1 else 0 end) as n_walk_in,
    count(value_twd)                                       as n_valued,
    sum(value_twd)                                         as total_value,
    max(value_twd)                                         as max_value,
    -- 中位數：SQLite 沒有 median()，用排序後取中間那一（兩）筆的平均。
    (select avg(value_twd) from (
        select value_twd,
               row_number() over (order by value_twd) as rn,
               count(*)     over ()                   as n
          from offers where value_twd is not null
     ) where rn in ((n + 1) / 2, (n + 2) / 2))             as median_value
from offers;

看這一題的 SQLqueries/02_value_by_category.sql
-- Q2 哪一類的生日優惠最大方？
--
-- 用中位數而不是平均：139 筆裡有幾個上千元的（樂園套票、套餐組）會把平均拉歪。
-- SQLite 沒有 median()／percentile_cont()，所以自己用 window function 做：
-- 先在每個 category 裡排序編號，再取中間那一（兩）筆平均；四分位同理。
with valued as (
    select category, value_twd,
           row_number() over (partition by category order by value_twd) as rn,
           count(*)     over (partition by category)                    as n
      from offers
     where value_twd is not null
),
stat as (
    select category,
           n,
           avg(case when rn in ((n + 1) / 2, (n + 2) / 2) then value_twd end) as median_value,
           avg(case when rn = max(1, n / 4)              then value_twd end)  as q1_value,
           avg(case when rn = max(1, (n * 3 + 3) / 4)    then value_twd end)  as q3_value,
           min(value_twd) as min_value,
           max(value_twd) as max_value
      from valued
     group by category, n
),
-- 全體中位數，當作比較基準
overall as (
    select avg(value_twd) as median_all from (
        select value_twd,
               row_number() over (order by value_twd) as rn,
               count(*)     over ()                   as n
          from offers where value_twd is not null
    ) where rn in ((n + 1) / 2, (n + 2) / 2)
),
counted as (
    select category, count(*) as n_all from offers group by category
)
select s.category,
       c.n_all,
       s.n                             as n_valued,
       cast(s.median_value as integer) as median_value,
       cast(s.q1_value     as integer) as q1_value,
       cast(s.q3_value     as integer) as q3_value,
       s.min_value,
       s.max_value,
       round(s.median_value / o.median_all, 2) as vs_overall
  from stat s
  join counted c on c.category = s.category
 cross join overall o
 order by s.median_value desc;

Q3

生日當天才想到，還來得及嗎？

生日當天才查，只剩一半能用。139 筆裡只有 68 筆（49%）是當天辦會員當天就能領；33 筆要你提前八天以上入會（多數是整整一個月），還有 32 筆（23%）品牌根本沒說要多久——對壽星來說，沒說＝不保證。

按「要提前幾天入會」分組的優惠筆數

看這一題的 SQLqueries/03_advance_days.sql
-- Q3 生日當天才想到要用，還來得及嗎？
--
-- advance_days = 這個優惠要求提前幾天完成入會／預約。0 表示當天辦當天用，
-- null 表示品牌沒明訂（對壽星來說等於「不保證」，所以單獨一欄，不混進 0）。
-- 重點是累積比例：用 sum() over (order by ...) 把「N 天前就要辦好」的優惠累加起來，
-- 才看得出「生日前一天才查，還剩多少可以用」。
with bucketed as (
    select case
             when advance_days is null then '未明訂'
             when advance_days = 0     then '當天辦就能用'
             when advance_days <= 7    then '要提前 1–7 天'
             when advance_days <= 30   then '要提前 8–30 天'
             else '要提前 30 天以上'
           end as bucket,
           case
             when advance_days is null then 9
             when advance_days = 0     then 0
             when advance_days <= 7    then 1
             when advance_days <= 30   then 2
             else 3
           end as sort_key,
           value_twd
      from offers
),
agg as (
    select bucket, sort_key,
           count(*)                      as n_offers,
           cast(avg(value_twd) as integer) as avg_value
      from bucketed
     group by bucket, sort_key
)
select bucket,
       n_offers,
       avg_value,
       round(100.0 * n_offers / sum(n_offers) over (), 1) as pct,
       -- 依門檻由鬆到緊累加：到這一列為止「拿得到」的優惠有幾筆
       sum(case when sort_key < 9 then n_offers else 0 end)
           over (order by sort_key rows between unbounded preceding and current row)
                                                          as cum_reachable
  from agg
 order by sort_key;

-- Q4 要先變成誰的會員，才換得到什麼？
--
-- 兩個分類交叉：入會方式（Ocard／品牌 APP／LINE／不用會員…）× 優惠型態
-- （免費無低消／免費有低消／買一送一／折扣）。SQLite 沒有 pivot，
-- 用 sum(case when ...) 把列轉成欄，最後一欄是這一種入會方式的優惠面額中位數。
with labelled as (
    select case membership_type
             when 'none'  then '不用會員'
             when 'app'   then '品牌 APP'
             when 'line'  then 'LINE 官方帳號'
             when 'ocard' then 'Ocard 第三方集點'
             when 'brand' then '品牌自家會員'
             when 'card'  then '指定信用卡'
             when 'tier'  then '要升到指定會員等級'
             else coalesce(membership_type, '未標註')
           end as access,
           membership_type,
           free_tier,
           value_twd,
           coalesce(advance_days, 999) as advance_days
      from offers
),
med as (  -- 每種入會方式的面額中位數
    select membership_type,
           avg(case when rn in ((n + 1) / 2, (n + 2) / 2) then value_twd end) as median_value
      from (
        select membership_type, value_twd,
               row_number() over (partition by membership_type order by value_twd) as rn,
               count(*)     over (partition by membership_type)                    as n
          from labelled where value_twd is not null
      ) group by membership_type
)
select l.access,
       count(*) as n_offers,
       sum(case when l.free_tier = 'free_no_min' then 1 else 0 end) as free_no_min,
       sum(case when l.free_tier = 'free_min'    then 1 else 0 end) as free_with_min,
       sum(case when l.free_tier = 'bogo'        then 1 else 0 end) as bogo,
       sum(case when l.free_tier = 'discount'    then 1 else 0 end) as discount,
       sum(case when l.advance_days = 0          then 1 else 0 end) as same_day_ok,
       cast(m.median_value as integer) as median_value
  from labelled l
  left join med m on m.membership_type = l.membership_type
 group by l.access, m.median_value
 order by n_offers desc;

-- Q5 這些優惠是誰說的？多久沒複查了？
--
-- 每筆優惠可以有多個來源，tier 越小越可信：1 品牌官方／2 新聞媒體／3 部落格懶人包／4 社群貼文。
-- best_source_tier 是其中最可信的那一個。這一題問的是資料治理，不是優惠本身：
-- 「最好的來源只是部落格」的優惠佔多少、這些優惠是不是反而面額開得特別大、
-- 以及距離上次複查過了幾天（julianday 相減）。
with t as (
    select case best_source_tier
             when 1 then '1 品牌官方'
             when 2 then '2 新聞媒體'
             when 3 then '3 部落格懶人包'
             when 4 then '4 社群貼文'
             else '未標註'
           end                                   as tier_label,
           coalesce(best_source_tier, 9)         as tier,
           verified,
           value_twd,
           cast(julianday('now') - julianday(last_checked) as integer) as days_since_check,
           (select count(*) from offer_sources s where s.offer_id = offers.id) as n_sources
      from offers
)
select tier_label,
       count(*)                                                as n_offers,
       round(100.0 * count(*) / sum(count(*)) over (), 1)       as pct,
       sum(verified)                                           as n_verified,
       round(100.0 * sum(verified) / count(*), 0)               as verified_pct,
       cast(avg(value_twd) as integer)                          as avg_value,
       round(avg(n_sources), 1)                                as avg_sources,
       max(days_since_check)                                   as days_since_check
  from t
 group by tier_label, tier
 order by tier;

各縣市可用的優惠筆數（含全台連鎖）

看這一題的 SQLqueries/06_county_coverage.sql
-- Q6 住在哪裡，生日優惠差多少？
--
-- v_offer_county 把兩種來源併起來：明確標了這個縣市的優惠，加上「全台」連鎖。
-- 這一題的重點是 window function 當分母：max(n_offers) over () 一次拿到全國最高的那個
-- 縣市，每一列就能直接算「跟最好的縣市差幾倍」，不用再開子查詢。
with per_county as (
    select c.name, c.area, c.order_no,
           (select count(*) from v_offer_county v where v.county = c.name)                      as n_offers,
           (select count(*) from v_offer_county v where v.county = c.name and v.via = 'region') as n_local,
           coalesce((select sum(n_stores) from store_counts s where s.county = c.name), 0)      as n_stores,
           coalesce((select count(distinct brand) from store_counts s where s.county = c.name), 0) as n_brands_with_store
      from counties c
)
select name                                                   as county,
       area,
       n_offers,
       n_local,                                               -- 其中是「限定這個縣市」的
       n_offers - n_local                                     as n_chain,  -- 其中是全台連鎖的
       n_stores,
       n_brands_with_store,
       rank() over (order by n_offers desc)                   as rk,
       round(100.0 * n_offers / (select count(*) from offers), 0) as pct_of_all,
       round(1.0 * max(n_offers) over () / nullif(n_offers, 0), 1) as gap_to_best,
       order_no
  from per_county
 order by n_offers desc, order_no;

Q7 · Q8

店開得多的品牌，生日禮是不是比較薄？

店開得越多，生日禮越薄。門市數最少的那四分之一品牌（1–3 家店）面額中位數 NT$180，最多的那四分之一（23–583 家）只有 NT$72。log10(門市數) 與面額的 Pearson 相關是 -0.284，弱負相關、不是強關係——26 家大連鎖裡還是有開 300 元的。這裡只有 106 個品牌有門市資料，所以是觀察，不是定律。

每一點是一個品牌：橫軸門市數（對數刻度）、縱軸優惠面額

按門市數四等分後的面額中位數

看這一題的 SQLqueries/07_footprint_vs_value.sql + 08_footprint_quartiles.sql
-- Q7 店開得多的品牌，生日優惠是不是比較小？（品牌層級的散佈資料）
--
-- 直覺上連鎖越大、單客成本壓得越低，生日禮應該越薄。這一題先把每個品牌的
-- 門市數跟優惠面額配成一組點，下一題（08）再算分位平均跟相關係數。
-- 門市數來自 store_counts（彙總），所以只有對得上的品牌會出現。
select o.brand,
       o.category,
       o.value_twd,
       f.n_stores,
       f.n_counties,
       o.free_tier,
       o.is_nationwide,
       ntile(4) over (order by f.n_stores) as store_quartile,
       -- 同類別裡的面額排名，拿來標出每一類最大方的那一家
       rank() over (partition by o.category order by o.value_twd desc) as rank_in_category
  from offers o
  join v_brand_footprint f on f.brand = o.brand
 where o.value_twd is not null
 order by f.n_stores desc;


-- ── 分組與相關係數：queries/08_footprint_quartiles.sql ──

-- Q8 把品牌按門市數分成四組，面額差多少？順便用純 SQL 算相關係數。
--
-- ntile(4) 把品牌依門市數切四等份，再比每一組的面額中位數。
-- 最後兩欄是 Pearson 相關係數，直接在 SQL 裡展開公式算：
--   r = (n·Σxy − Σx·Σy) / √(n·Σx² − (Σx)²) · √(n·Σy² − (Σy)²)
-- x 取 log10(門市數)：門市數從個位數到上千家，不取對數的話幾家超大連鎖會主導整個係數。
-- 四組的值相同（同一個母數算出來的），放在每一列只是方便一起讀。
with bv as (
    select o.brand, o.value_twd as y, f.n_stores,
           log10(f.n_stores) as x,
           ntile(4) over (order by f.n_stores) as q
      from offers o
      join v_brand_footprint f on f.brand = o.brand
     where o.value_twd is not null
),
med as (
    select q,
           avg(case when rn in ((n + 1) / 2, (n + 2) / 2) then y end) as median_value
      from (select q, y,
                   row_number() over (partition by q order by y) as rn,
                   count(*)     over (partition by q)            as n
              from bv)
     group by q
),
corr as (
    select count(*) as n, sum(x) as sx, sum(y) as sy,
           sum(x * y) as sxy, sum(x * x) as sxx, sum(y * y) as syy
      from bv
)
select bv.q                                                as store_quartile,
       count(*)                                            as n_brands,
       min(bv.n_stores)                                    as min_stores,
       max(bv.n_stores)                                    as max_stores,
       cast(med.median_value as integer)                   as median_value,
       cast(avg(bv.y) as integer)                          as avg_value,
       round((corr.n * corr.sxy - corr.sx * corr.sy) /
             (sqrt(corr.n * corr.sxx - corr.sx * corr.sx) *
              sqrt(corr.n * corr.syy - corr.sy * corr.sy)), 3) as pearson_r,
       corr.n                                              as corr_n
  from bv
  join med  on med.q = bv.q
 cross join corr
 group by bv.q, med.median_value, corr.n, corr.sx, corr.sy, corr.sxy, corr.sxx, corr.syy
 order by bv.q;

-- Q9 哪幾筆已經不能用了？（資料維運清單）
--
-- validity_type = 'fixed' 的優惠是限期檔期，有 valid_from／valid_until；
-- rolling 是每年都有的常態優惠。對一個會被壽星拿去用的網站來說，
-- 「檔期過了還留在頁面上」比「少收錄一筆」嚴重，所以這一題直接產出要處理的清單：
-- 過期、快到期（14 天內）、還沒開始、以及沒寫迄日的 fixed（等於沒辦法自動下架）。
select brand,
       category,
       valid_from,
       valid_until,
       value_twd,
       best_source_tier,
       verified,
       case
         when valid_until is null                             then '沒寫迄日'
         when julianday(valid_until) <  julianday('now')      then '已過期'
         when julianday(valid_from)  >  julianday('now')      then '還沒開始'
         when julianday(valid_until) <= julianday('now') + 14 then '14 天內到期'
         else '進行中'
       end                                                     as status,
       cast(julianday(valid_until) - julianday('now') as integer) as days_left,
       cast(julianday('now') - julianday(last_checked) as integer) as days_since_check
  from offers
 where validity_type = 'fixed'
 order by case
            when valid_until is null                        then 1
            when julianday(valid_until) < julianday('now')  then 0
            else 2
          end,
          valid_until;

怎麼做的

九個問題、九個 .sql 檔，全部跑在 SQLite。統計量刻意全部寫在 SQL 裡： 中位數與四分位用 row_number() over (partition by …) 自己做 （SQLite 沒有 percentile_cont）、累積比例用 sum() over (order by …)、分組用 ntile(4)、 Pearson 相關係數直接把公式展開成 sum(x*y) 那幾項算。 Python 只負責兩件事：把巢狀 JSON 攤平成可以 join 的表，以及把查詢結果排成這一頁。

沒有第三方套件。pandas／matplotlib 都沒用到， 圖是直接產 inline SVG：中文不會因為缺字型變成方塊、深色模式用 CSS 變數自動切換、 整份報告就是一個 HTML 檔。

analysis/
├ build_db.py      JSON → SQLite（含門市彙總，653 列 CSV 進版控）
├ schema.sql       分析庫的 DDL 與兩個 view
├ queries/         01…09，一題一檔
├ charts.py        inline SVG：橫條、直條、散佈、交叉表
├ report.py        跑查詢 → 算結論 → 吐這一頁
└ data/store_counts.csv   品牌×縣市門市數（原始 Places 回應不進 git）

重跑：python build_db.py && python report.py。 門市明細在本機才有，缺的時候會自動改讀 data/store_counts.csv， 所以 clone 下來就跑得完整份報告。

資料限制（先說清楚再看結論）

  • 這是快照，不是即時資料。優惠來自 offers.json， 最後查證日 2026-08-04；線上版的 Postgres 已經長得更大， 但這台機器跑分析時（2026-11-03）線上資料庫正好在維護，所以全部用本機快照。 Q9 的「全部過期」是快照的必然結果，不是線上網站的狀態。
  • 面額是估的。value_twd 是把「一份雞塊」「九折」這種優惠 換算成新台幣的估計值，16 筆估不出來（吃到飽、 「依門市公告」）就留 null，不當 0。所有平均與中位數都只算得出來的那些。
  • 門市數只到對得上的品牌。門市來自 Google Places 的品牌搜尋結果， 117 個品牌抓得到門市，其中 106 個同時估得出面額—— Q7 的散佈圖就是這 106 個點。品牌名對不上的（聯名卡、改名、小店） 沒有門市數，所以這一題天生偏向連鎖品牌。
  • 縣市覆蓋看的是「有沒有」，不是「多好拿」。Q6 算的是這個縣市有幾筆優惠， 沒有按人口或店數標準化——手上沒有可引用的人口資料，寧可不換算， 也不要生一個看起來精確的數字。
  • 沒有使用者行為資料。這份分析完全是優惠與門市的靜態結構， 沒有碰任何人的瀏覽或兌換紀錄。
