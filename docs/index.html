這三個產品都是同一件事的不同版本：把沒人幫你算的事算出來。 銀行幫你算錢，公司幫你算工時，剩下那些呢？你今年進了幾次 live house、 一年一次的那天究竟省下多少，算出來其實很有意思。

這份作品集要給的不是「我做了三個 app」，而是這三個產品背後我怎麼做決定： 要衡量什麼、資料從哪來、算出來之後改了什麼、改完有沒有用。 有數據的地方放數據，還沒有的地方直接標成「待補」，不先填一個看起來合理的數字。

我怎麼做產品分析

每個案例都照同一個順序走，所以三頁讀起來是同一套方法的三次應用。

1. 先定義要衡量什麼

做之前先寫下來：這個產品好不好，看哪幾個數字。壽星日分成供給（有多少優惠能拿）、 需求（有沒有人真的用）、品質（資料可不可信）、成本（跑得起來嗎）四組； RelateStats 因為收不到行為資料，整組指標得換一套寫法。

2. 資料從哪來，界線在哪

壽星日的事件表 site_events 是自己設計的，欄位只有事件類型、 一個匿名的 session、選填的使用者 id 跟一包 meta。分析一律只用彙總， 個人層級的紀錄不離開資料庫，也不進版控。 這一頁公開在網路上，所以這條線要先畫好再開始算。

3. 算完要能導向一個決定

不以「做出一張圖」為終點。「19 筆限期優惠全部過期」要推到 「不能靠人記得下架，得用 valid_until 自動判斷」； 「資料庫流量超額」要推到「哪一條路徑吃掉最多、先砍哪一條」。

4. 改完要回去看數字

154 個版本都有紀錄，改動大的會回頭量一次。 把快取從 10 分鐘拉到 30 分鐘之後，上游請求從一天 144 次降到 48 次； 一批減量上線之後，每天的量從 115 MB 降到 85 MB。 沒有回去量的就不敢說它有效。

具體會的東西

  • SQL。九支查詢全部用 window function 跟 CTE 寫完：中位數與四分位 （SQLite 沒有 percentile_cont，自己用 row_number() 做）、 累積比例、ntile(4) 分組、交叉表、Pearson 相關係數直接展開公式算。 每一題的 SQL 都附在報告裡。
  • Python。把巢狀 JSON 攤平成可以 join 的表、彙總成可以進版控的 CSV、 再把查詢結果排版成這幾頁。沒有第三方套件，圖是自己產的 inline SVG。
  • 事件追蹤設計。事件表的欄位、哪些事件要記、匿名 session 怎麼接， 以及「公開的排行榜數字」跟「內部的分析數字」為什麼不能共用同一個定義。
  • 成本分析。把一次流量超額拆成固定成本與變動成本，量出每條路徑的位元組， 按「真的會發生」排風險順序，再決定砍哪一條。
  • 資料治理。來源分級（官方／媒體／部落格／社群）、複查延遲、 過期自動下架，都是從分析結果長出來的規則。
