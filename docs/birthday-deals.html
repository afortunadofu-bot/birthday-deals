分析一：供給面

完整的九題在報告那一頁，這裡只留跟產品決策有關的三個。

住在哪裡，差 3.5 倍

住台北市的壽星有 115 個優惠可選， 最少的縣市只有 33 個，而且那些全部是全台連鎖， 等於這些縣市完全沒有本地品牌的生日優惠可拿。這是產品的供給缺口， 不是演算法調一調就會好的東西。

一半的優惠，生日當天才查就來不及

49% 的優惠是當天辦會員當天就能領，其餘要提前登錄， 還有 32 筆品牌根本沒寫要多久。對一個「生日當天才會被打開」的產品來說， 這直接決定了要不要做提前提醒，答案是要。

只有 12% 的優惠有品牌官方背書

其餘的最佳來源是部落格懶人包或社群貼文。這不是「資料很爛」， 是「這類資料本來就長這樣」，所以產品要承認它：來源分級顯示在卡片上、 使用者可以回報有沒有用、過期的自己下架。

分析二：成本與可靠性

2026 年 10 月，Supabase 的免費額度（Egress 5 GB／月）被判超額，整個專案被停權， 登入、收藏、回報、投稿全部不能用。這一段是把它當成一個分析題來處理的過程。

先分清楚是事故還是日常

逐日看 log 的量：9/20～9/28 是 70～110 MB／天，9/30 之後跳到 450～540， 10/04 最高 830 MB。對得上 10/02～10/04 的資料庫事故—— 掃全表的查詢把 API 打到一直回 522。修好的隔天就掉回來了。 所以超額是一次事故造成的，不是日常流量撐不住，這個結論決定了後面要做什麼： 要防的是「下一次事故」，不是「使用者變多」。

量每一條路徑到底吐出多少位元組

不猜，實際量。優惠清單壓縮後一次 128 KB、/board 合計 33 KB、 /stats 約 1 KB，一輪回源約 180 KB。快取 30 分鐘一輪， 一天 48 輪，一個機房一個月約 0.26 GB——而 Cloudflare 是每個機房各一份快取， 三四個機房就是一個月 1.1～1.4 GB 的固定成本。這部分跟有幾個使用者完全無關， 是先要認的帳。

照「真的會發生」排，不是照「砍得最多」排

有一條原本以為很肥的查詢，實際量完壓縮後只有 354 bytes，就放掉不做了。 真正做的三件事：快取 10 分鐘拉到 30 分鐘（上游請求一天 144 → 48 次， 每個機房每月 0.6 → 0.2 GB）、優惠清單從 select=* 改成逐欄點名 （146 → 128 KB，砍掉五個前端根本沒在讀的欄位）、 還有一批把請求數減半的改動（每天的量 115 → 85 MB，約少 25%）。

回頭看有沒有用

用量頁從 1.284 GB 掉到 0.896 GB，跟自己算的對得起來。 但這次仍然被停權，因為被判的是上一個計費週期——事故那三天就在裡面。 所以同一批分析也產出了一條維運規則：加新的 RPC 或 view 的時候要特別小心， 走快取的有擋，前端直接打的沒有。

數字出處：repo 裡的 SUPABASE-流量.md，2026-10-20 實測。

分析三：使用者行為（等資料）

這是這個案例現在唯一的空白，而且空白的原因是技術性的： 資料庫停權中，讀不到任何一筆事件。

能先做的都做了：事件表本來就設計好了，分析要用的指標也定義完了 （上面那張表的「需求」那幾列）。事件表長這樣：

site_events(
  id          bigserial,
  event_type  text,        -- pageview / submit / use_report / wish / rate / static_view …
  session_id  text,        -- 匿名，localStorage 產生
  user_id     uuid,        -- 可為 null（沒登入也能用）
  meta        jsonb,
  created_at  timestamptz
)

要算的是三件事：漏斗（到站 → 點開優惠 → 點外連或收藏 → 回報用過）、 內容供給與需求對不對得上（最多人收藏的類別，跟優惠數最多的類別是不是同一批）、 以及回訪（生日是一年一次的事件，所以留存要看的是「隔年還會不會回來」， 不是次日留存）。

已經寫好、等資料就會亮起來的部分

有一半不用等管理員權限。線上有四支 view 本來就開放公開讀 （offers_public、wishlist_counts、most_wished、 leaderboard_monthly），裡面有每筆優惠的回報數、兌換成功率、 留言數與收藏數——那已經是需求面的一半。抓這四支的程式 （fetch_live.py）跟吃它的 ETL（build_db.py --live）都寫好了， 現在跑會停在一句「Supabase 回 402」。

兩支對應的查詢也先寫完了： 10_demand_vs_supply.sql 比「哪一類收藏多」跟「哪一類優惠多」的落差， 用來決定下一批要去談哪種品牌； 11_offer_health.sql 挑出回報多、成功率低的優惠，那是資料錯了或品牌改規則， 屬於維運清單。

真正要等管理員匯出的只剩漏斗跟回訪，因為 site_events 是 admin 限定、anon key 讀不到。

公開的只會是彙總。個人層級的事件不離開資料庫，也不進版控。

決策紀錄（節錄）

  1. v129快取 10 分鐘 → 30 分鐘

    成本分析的直接結果：上游請求一天 144 → 48 次。代價是新優惠最多晚 30 分鐘出現，對一個「一年用一次」的產品可以接受。

  2. v132優惠清單從 <code>select=*</code> 改成逐欄點名

    量完才發現有五個欄位前端一個都沒讀。146 → 128 KB。順手加了一條測試：view 以後加欄位沒跟著改，測試就會紅。

  3. v133標「全台」但其實沒那麼全台的，改成實際有分店的縣市

    門市資料跟優惠的 regions 欄位對不起來，是縣市覆蓋那一題算出來的。影響的是使用者在自己縣市看到的清單準不準。

  4. v144自動上架：老手的新投稿不用再等審核

    投稿審核是人工瓶頸。先看投稿者過去的紀錄，再決定要不要擋。

  5. v167「我省下多少」收成一個數字，排到「我送出過的」前面

    這個產品的核心價值是「幫你算省下多少」，版面要讓它第一眼就看得到。

  6. v168–v172資料庫停掉時，自動掛「系統更新中」、錯誤訊息一律中文

    停權期間使用者看到的是英文錯誤。可靠性也是產品的一部分：壞掉的時候要壞得像話。

還沒做到的

  • 使用者行為那一段還是空的。資料庫恢復之後要補完漏斗、回訪與內容供需。
  • 優惠筆數要換成現在的。這一頁用的是 2026-08 的快照（139 筆）， 線上實際已經成長到好幾百筆，等得到資料就重跑。
  • 縣市覆蓋沒有按人口標準化。手上沒有可引用的人口資料，所以先不換算。
